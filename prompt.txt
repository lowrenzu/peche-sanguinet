Oui. Voici un **prompt maître**, conçu pour être donné à une IA de développement (Replit Agent, Cursor, Claude Code, Codex, etc.) afin qu’elle ne crée pas seulement une maquette, mais **une application fonctionnelle et évolutive**.

### Prompt maître — PêcheSanguinet / Fishing Forecast

# PROMPT MAÎTRE — PÊCHESANGUINET

## Application intelligente de prévision de pêche — Lac de Cazaux-Sanguinet, France

Tu es un **Lead Product Designer + UX/UI Designer + Full-Stack Engineer + Data Engineer + Data Scientist spécialisé dans les systèmes prédictifs environnementaux**.

Ta mission est de concevoir et développer une application web/mobile moderne appelée :

# 🎣 PÊCHESANGUINET

### Fishing Forecast — Lac de Cazaux-Sanguinet

L'objectif est de créer un véritable **outil d'aide à la décision pour la pêche des carnassiers**, centré exclusivement sur le secteur de Sanguinet et le lac de Cazaux-Sanguinet.

L'application doit exploiter des **données météorologiques actuelles, prévisionnelles et historiques**, des données relatives à la température de l'eau et, progressivement, les observations réelles des pêcheurs.

Le système doit être **scientifique, transparent, explicable et basé sur des données**.

NE PAS utiliser :

* astrologie
* phases lunaires comme facteur prédictif principal
* croyances populaires non vérifiées
* pseudo-science
* scores arbitraires présentés comme des vérités scientifiques

---

# 1. OBJECTIF PRINCIPAL

L'application doit répondre à une question simple :

> "Est-ce que les conditions actuelles et prévues sont favorables à l'activité des carnassiers sur le lac de Cazaux-Sanguinet, et quand est-il statistiquement le plus intéressant de pêcher ?"

Le système doit produire :

## INDICE DE FRÉNÉSIE — IF

Score de 0 à 100.

Exemple :

**82 / 100**
TRÈS FAVORABLE

Mais le score ne doit jamais être affiché seul.

L'application doit toujours expliquer :

* pourquoi le score est élevé ou faible ;
* quels facteurs influencent le résultat ;
* quelle donnée a le plus d'impact ;
* comment les conditions évoluent ;
* quel créneau horaire semble le plus favorable ;
* quel est le niveau de confiance de la prédiction.

## Historique

Construire une base historique permettant de comparer les conditions actuelles avec :

* les jours précédents
* les mêmes périodes saisonnières
* les années précédentes
* les situations météorologiques similaires

* Météo-France / données publiques lorsque pertinentes
* autres sources fiables si nécessaire

IMPORTANT :

Ne jamais mélanger silencieusement plusieurs sources incompatibles.

Chaque donnée doit conserver :

* source

* unité

* statut observation/prévision
* éventuellement qualité/confiance

# 4. TEMPÉRATURE DE L'EAU

La température de l'eau est une donnée centrale.

Ne jamais remplacer automatiquement la température de l'eau par la température de l'air.

Créer un module spécifique :

## WATER TEMPERATURE ENGINE

Il doit pouvoir gérer :

* température actuelle de surface
* historique
* évolution 6 h
* évolution 12 h
* évolution 24 h
* évolution 72 h
* moyenne mobile
* anomalie par rapport à la normale saisonnière

Prévoir plusieurs méthodes d'acquisition :

1. station de mesure lorsqu'elle existe ;
2. données publiques ;
3. données environnementales ;
4. estimation/modélisation clairement identifiée comme telle.

Si une donnée est estimée, l'interface doit l'indiquer explicitement :

**Température estimée — confiance moyenne**

Ne jamais présenter une estimation comme une mesure réelle.

Créer un moteur modulaire appelé :

### Pression et variation de pression

20 %

### Vent

20 %

### Nébulosité / luminosité

15 %

15 %

NE PAS considérer ces coefficients comme scientifiquement définitifs.

Ils constituent uniquement le modèle V1.

# 6. ANALYSE DES VARIATIONS

Le moteur doit privilégier les **tendances et variations** plutôt que les valeurs isolées.

Exemple :

Une pression de 1015 hPa seule ne signifie pas automatiquement "bonne pêche".

Analyser :

* pression actuelle
* pression à -3 h
* pression à -6 h
* pression à -12 h
* pression à -24 h

Calculer :

* variation
* vitesse de variation
* stabilité
* tendance

Même principe pour :

* température de l'eau
* vent
* couverture nuageuse
* température de l'air

## WIND MAP

# 9. CONFIANCE DU MODÈLE

Ajouter un deuxième indicateur :

## CONFIANCE

Exemple :

**78 % de confiance**

La confiance dépend notamment :

* quantité de données disponibles
* fraîcheur des données
* qualité des mesures
* cohérence des différentes sources
* quantité d'historique comparable

IMPORTANT :

Un score de pêche élevé avec une faible confiance doit être présenté comme tel.

Exemple :

> IF 84/100
> Confiance : 54 %
>
> "Conditions théoriquement très favorables, mais peu de situations historiques comparables."

# 10. SIMILARITÉ HISTORIQUE

Créer un moteur :

## HISTORICAL MATCHING ENGINE

Il recherche dans l'historique les journées présentant des conditions similaires.

Comparer :

* température eau
* température air
* pression
* évolution pression
* vent
* direction vent
* nébulosité
* saison
* heure

Afficher par exemple :

> 27 journées historiques similaires trouvées.

Puis :

> Activité favorable dans 68 % des situations comparables.

ATTENTION :

Ne pas inventer de statistiques si aucune donnée réelle de captures n'existe.

Faire la distinction entre :

### Similarité météorologique

et

### Probabilité réelle de capture

Tant que l'application ne possède pas suffisamment de données de pêche, parler de :

**"conditions historiquement similaires"**

et non de :

**"probabilité de prendre un brochet".**

# 36. OBJECTIF FINAL

Le produit final doit donner l'impression d'un :

## "Bloomberg Terminal de la pêche"

mais simplifié pour un pêcheur.

À l'ouverture :

**"Voici ce qui se passe actuellement sur le lac."**

Puis :

**"Voici comment les conditions vont évoluer."**

Puis :

**"Voici les créneaux les plus intéressants."**

Puis :

**"Voici pourquoi le modèle pense cela."**

Et enfin :

**"Voici ce que les données historiques et vos propres captures permettent d'apprendre."**

Le système doit devenir progressivement **spécifique au lac de Cazaux-Sanguinet**, plutôt qu'un simple agrégateur météo.

Ce prompt est volontairement conçu pour éviter un piège fréquent : **faire une belle interface météo qui prétend prédire la pêche sans disposer des données nécessaires**. La V1 produit un indice environnemental explicable ; les captures réelles permettront ensuite de construire un modèle statistique réellement spécifique à Sanguinet.
